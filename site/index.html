The difference

Agents and workflows are built first

Before any UI exists, the AI agents the app needs are created and tested, wired into workflows, and given their own secure tokens. The app is then generated on top of them.

  • Real agents, versioned, with input and output schemas.
  • Branching workflows with human approval steps where it matters.
  • The app calls them through tokens written into its config, never hard-coded.

Then the app, designed for you

Not one template, reskinned

A design pass picks the layout, palette and type for each app. Pages are generated in parallel, type-checked and repaired, and the app opens in a live preview. These came from one-line prompts:

Agent Hub

Every agent you make lives here

Agents are versioned like code. Test one, look at its runs, compare versions, or restore an old one.

  • Describe an agent in plain English and the Studio drafts it: purpose, tools, guardrails and schemas.
  • Guardrails and permissions are enforced at run time, not just suggested in a prompt.
  • Human in the loop: require approval of outputs or of specific tools.

Workflows

Wire agents together, visually

An n8n-style canvas: drag in agents and logic, branch on an agent's answer, and ask a person before anything goes out. Then talk to the workflow in the Playground.

  • Trigger, agent, branch, approval, HTTP and output nodes.
  • Every run is recorded and can be replayed on the canvas.
  • Saved as versions in git, so nothing is lost.

New · APIs

Every agent and workflow is an API

Create an agent on the platform, click Get API, and call it from your own workflows and apps: n8n, Zapier, Make, a script or your backend.

  • One token per agent or workflow, shown once, stored only as a hash, revocable any time.
  • Ready-to-paste code in curl, JavaScript and Python, plus an n8n workflow download.
  • Same rules as inside: the agent's tools, guardrails, approvals and your AI limits still apply.
# Run an agent from anywhere
curl -X POST https://<monarch-host>/hooks/agents/triage/run \
  -H "Authorization: Bearer $MONARCH_AGENT_TOKEN" \
  -d '{"input": {"task": "Sort this email by urgency"}}'

# Response
{ "status": "completed",
  "output": { "urgency": "high" } }

The IDE · for developers

Your repo, in a sandbox, with a live preview

Open any GitHub repo, private ones included. The stack, services and ports are detected and shown to you before anything runs.

  • Monaco editor, a terminal inside the container, logs and a preview on its own origin.
  • 20+ stacks on 14 sandbox images: Node, React, Next.js, Python, Go, Rust and more.
  • Paste any repo URL into Run a repo to get it live without opening the IDE.

Coding agents

Plan first, then a team builds it

Ask for a change and review the plan like a design doc, with inline comments. Then a team of coding agents builds it task by task and explains what changed.

  • Agents live in your repo as plain files, each owning its part of the code.
  • Guardrails enforced in code: edit and command guards run on the real content.
  • The AI proposes, the server decides: risky commands need your approval.

GitHub

Synced with GitHub, both ways

Commit, push to a new branch and open a pull request from the IDE. Apps made in Build mode are pushed to your GitHub automatically, private by default, with a README.

  • Your token never enters the sandbox: fetch and push run in a separate container that runs no repo code.
  • Secret files never reach GitHub; blank examples like .env.example are committed instead.

Under the hood

Built to treat every repo, prompt and browser as untrusted

Sandboxes

One container per project

CPU, memory and process limits, no extra privileges, only the project folder mounted.

Server

One Go binary

UI and templates embedded, with a Node service beside it for agents, the Hub and workflows.

Data

MongoDB

Users, projects, agents, workflows and runs. Secrets encrypted; API tokens kept only as hashes.

Identity

Sign in your way

GitHub, Google or a beta code. Who you are comes from your session, never from the page.

Files

Stay inside the project

Every read and write goes through a guarded root that refuses path escapes and symlinks.

Tested

Including the attacks

170+ automated tests, with negative ones: other users' ids, path escapes and hostile repos.
